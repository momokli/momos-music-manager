## Contract feasibility

The contract's structure is sound, but several specifics will not work as written.

**Blocking / high-severity**

1. **Playlist ingestion is largely impossible as assumed.** `GET /playlists/{id}/items` returns items only for playlists the user **owns or collaborates on**; merely *followed* playlists yield **metadata only, no `items`** (403 on the items endpoint). Since the Hub's purpose is cross-user overlap of playlists, and DJs mostly *follow* other people's playlists, most playlist track data is unreachable. `hub_playlists`/`hub_playlist_tracks` will be empty or owner-only. **Recommendation:** scope v1 ingest to **owned/collaborative playlists** plus **liked tracks** (`user-library-read`, which is unaffected), and say so explicitly; treat "followed playlist ingest" as out of scope until/unless Extended Quota Mode (unreachable for this project).

2. **The 5-user cap contradicts "multi-user."** Dev mode allows **5** authorized users, each allow-listed in the dashboard, and the **app owner must have Premium**. "Milestone M3: cross-user dedup proven" still works, but only within ≤5 hard-coded users. **Recommendation:** state the cap in the contract and stop treating Extended Quota Mode as a fallback.

3. **6-month refresh-token expiry.** The schema stores `refresh_token`/`token_expiry` but the contract has no re-auth path. A stored token silently dies after ≤6 months (and any token older than that is invalidated on first use). **Recommendation:** store the **authorization timestamp** (or derive from `connected_at`), treat `invalid_grant` as "reconnect needed", and expose that state via `/api/hub/me` (`connected:false` / needs reauth) rather than failing ingest.

**Medium**

4. **Redirect-URI / TLS ordering.** The Spotify redirect is at `192.168.178.200`, which is **not** loopback, so `http://` is rejected → the callback **must be HTTPS**. But the contract only delivers HTTPS in **M4**, while Spotify link/ingest (redirect) is **M3**. Either M3 must already be reachable over HTTPS (self-signed cert on the LAN; note browsers/`reqwest` trust implications) or the Spotify callback must be tunnelled. This ordering should be fixed or called out.

5. **OIDC issuer must be HTTPS.** `openidconnect`'s `IssuerUrl` requires the `https` scheme, so Pocket ID must be served over HTTPS (or behind a TLS terminator) **before M2**, not just by M4. Same "M2 needs HTTPS early" tension as above.

6. **`hub_playlist_tracks` PK is wrong for real playlists.** `PK(playlist_id, track_id)` collapses **duplicate occurrences** of the same track and gives a single `position`. Spotify playlists can contain the same track multiple times. Use a surrogate row id or `PK(playlist_id, position)` (or include `position`), and keep `added_at` per row.

7. **Nullable / non-track items.** Playlist items can be **local files** (`is_local: true`) or **episodes** (`type:"episode"`; `additional_types`). A local track may carry no usable Spotify track id, which breaks `hub_tracks.service_track_id NOT NULL` and `hub_tracks.isrc`. Filter to `type == "track"` and non-local on ingest, and make `isrc` nullable.

**Low / informational**

8. **ISRC is not an identity.** Keep `UNIQUE(service, service_track_id)` as the dedup key (as written) and do **not** add a unique constraint on `isrc`. "Cross-user dedup" should be proven on `service_track_id`, not ISRC.

9. **Rate/quota planning.** Dev-mode limits are lower and now **per developer account**; batch endpoints are gone, so ingest must page playlist items at `limit ≤ 50` and back off on 429 using `Retry-After`, and treat `reason:"QUOTA_EXCEEDED"` (no `Retry-After`) as a slower, non-retryable-immediately condition. Because playlist-items responses embed full track objects, the removed `GET /tracks` batch endpoint is **not** strictly needed — avoid rspotify's deprecated `tracks()`.

10. **rspotify version.** The pinned `0.15` is pre-Feb-2026; `0.16.x` is the API that tracks the removals. No contract change is *required* for read-only ingest, but the ingest code must not call endpoints 0.15 still exposes but Spotify removed (`tracks()`, `artists()`, `albums()`, `user()`, browse/category/new-releases). Consider bumping the pin to `0.16`.

11. **Contract paths/schema otherwise fine.** The HTTP surface (`/api/hub/*`), `501` for non-Spotify services, env-key names, `hub_`-prefixing, and the four overlap **views** are all implementable; `hub_v_shared_tracks` (`HAVING count(distinct user_id) >= 2`) and `hub_v_user_overlap` are straightforward over `hub_playlist_tracks ∪ hub_liked_tracks`. The guarded read-only SQL console is a policy risk, not a technical blocker (keep `HUB_SQL_CONSOLE_ENABLED=false` by default and run read-only).
